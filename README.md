# Mailroom — AI Inbox Assistant for Small Businesses

A multi-tenant Gmail assistant that reads incoming customer emails, classifies them, and writes on-brand draft replies for a human to review and send.

Designed for small businesses with public-facing inboxes (`info@`, `contact@`, `hello@`) — where the same handful of questions arrive every day, the answers are personal and brand-specific, and nobody has time to write them.

---

## The problem this solves

Owner-operated small businesses live in their inbox. The mix is roughly:

- 40% repetitive questions whose answers are obvious if you know the business — schedules, pricing, "is this for me," basic policy
- 30% nuanced questions that need a personal answer
- 20% notifications, vendor pitches, automation
- 10% things that need careful handling (refunds, complaints, anything emotionally loaded)

Today, most owners burn 5–10 hours a week typing variations of the same five emails. Generic AI assistants don't help much: they don't know the business, they don't sound like the brand, and they can't be trusted with sensitive replies. Owners end up with a tool that can draft "feel free to reach out" boilerplate but can't actually answer "what time is your Tuesday class?" or "do you offer family rates?"

This project fills that gap.

---

## What it does

A Python service runs continuously, polling Gmail every 60 seconds.

For each unprocessed thread:

1. **Filter** — cheap rules drop obvious non-candidates (mailing-list bounces, no-reply senders, threads with an existing human draft, our own outbound) before any LLM is invoked
2. **Classify** — Claude Sonnet 4.6 reads the thread alongside the tenant's knowledge base and returns a structured decision: `should_draft`, `category`, `sensitivity`, `confidence`, `reason`
3. **Gate sensitive content** — anything classified as high-sensitivity (refunds, complaints, legal, emotionally loaded) gets labeled `flag-for-human` and **never receives a draft**, regardless of how confident the model was
4. **Draft** — for everything else, Claude generates a body in the tenant's voice, grounded in their knowledge base. The system prompt and KB are prompt-cached, so per-email cost stays under ~$0.015
5. **Render** — the body is sanitized (HTML injection defense), converted to HTML, and wrapped in the tenant's Jinja signature template
6. **Save** — the draft is attached to the original Gmail thread via `messages.insert`, so the owner reviews it in Gmail's native UI alongside the customer's message
7. **Persist** — every draft, classification, and skip is logged to Postgres for auditing and tuning

A daily sweep then compares each draft to what the owner actually sent, computing edit-distance to flag where drafts are landing well vs being heavily rewritten — feedback for ongoing prompt and KB tuning.

## Quality bar — why drafts feel real, not generic

This is what separates the product from a generic AI plugin.

- **Brand voice with few-shot examples.** Each tenant has a `voice.md` with tone rules, forbidden phrases ("I hope this email finds you well", em-dash flourishes, "Certainly!"), and 5–7 worked examples of "this is what a great reply looks like." The LLM mimics the examples more than abstract instructions.
- **Knowledge-base grounding.** Every factual claim in a draft must come from the tenant's markdown knowledge base. If the answer isn't there, the system says so honestly and offers a follow-up rather than inventing.
- **Sensitive categories never get drafted.** Refunds, complaints, anything emotionally loaded reach a `flag-for-human` label and the human writes from scratch. Better silent than wrong.
- **Real signature, not a generic footer.** Each tenant's signature is an HTML Jinja template with brand color, contact details, and social links — rendered server-side, not generated by the LLM.
- **Drafts attached to threads.** Owners review in Gmail's compose UI right next to the customer's message — no separate dashboard, no new tool to learn.

### Component boundaries

Each module has one job and a narrow public interface. Internals can change without breaking other modules — which is what makes the multi-tenant evolution achievable as a config change rather than a rewrite.

| Module | Responsibility |
|---|---|
| `gmail_client/` | Wrap the Gmail API. Only place in the codebase that knows Gmail exists. |
| `filters/` | Rule-based pre-filter. Skips obvious non-candidates with zero LLM cost. |
| `classifier/` | LLM-powered gate. Returns structured `Classification`. |
| `drafter/` | Body generation with prompt caching on KB + voice + system prompt. |
| `knowledge/` | Per-tenant markdown loader with mtime-based cache + content hash for versioning. |
| `renderer/` | Markdown → HTML, bleach sanitization, Jinja signature wrapping. |
| `feedback/` | Daily sweep: diff drafts vs actually-sent, categorize outcome. |
| `db/` | SQLAlchemy 2 models, connection pool, idempotent migrations. |
| `pipeline/` | Orchestrator. Per-stage error isolation; one bad email never stops a tick. |
| `alerts/` | Best-effort SMTP alerting on real failures (auth, KB parse, error-rate spikes). |

### Multi-tenant by design

Today the system runs one tenant per deployment. The architecture is positioned for multi-tenant SaaS without a rewrite:

1. **Per-tenant content isolated to `tenants/<name>/`** — adding tenant #2 means adding a folder, not editing code
2. **Tenant boundary at the loader, not in business logic** — `KnowledgeLoader.load("acme")` already takes a tenant name; downstream code just consumes a `KnowledgeBundle`
3. **Tenant column on every DB table** — `draft_records.tenant`, `skip_records.tenant`, `error_records.tenant` already exist
4. **Service account auth path planned** — for Workspace customers, a domain-wide-delegated service account replaces the OAuth refresh-token cycle, sidestepping Google's restricted-scope verification entirely

What's not built but ready to bolt on: per-tenant Gmail credentials in DB (instead of env vars), a web admin for KB editing, and Google Sheets sync for tabular content like schedules.

### Engineering decisions worth calling out

- **TDD throughout the pure-logic modules.** `filters/`, `knowledge/`, `renderer/`, `feedback/diff.py` were all written failing-test-first. 22 unit tests cover the boring-but-load-bearing surfaces.
- **Real Gmail + real Claude in the integration tests, no mocks.** Mocks lie; the integration tests cost ~$0.30 to run end-to-end and catch issues that mocks would mask.
- **Golden email harness.** A YAML of 10 hand-crafted scenarios (drafted / skipped / flagged) get seeded into the test inbox; the pipeline runs over them and outcomes are asserted via the resulting Gmail labels and DB rows. Caught real classification bugs during development.
- **Pipeline error isolation.** Per-stage `try/except` records each failure to Postgres and continues to the next thread. Critically, the `processed` Gmail label is only applied AFTER the draft is created and recorded — so a DB outage in the middle of a tick doesn't cause double-drafting on the next run.
- **HTML sanitization on the body.** LLM output is sanitized with bleach before being wrapped in the signature template. Defense-in-depth in case the model ever echoes hostile HTML from a customer message.
- **Prompt caching.** The drafter caches three blocks (system prompt, voice guide, knowledge base) — the per-email cost is dominated by output tokens and the small variable user prompt, not the 3000+ tokens of static context.

## Tech stack

- **Language:** Python 3.13 (managed with `uv`)
- **LLM:** Anthropic Claude Sonnet 4.6 (with optional Opus 4.7 escalation for medium-sensitivity drafts)
- **Email API:** Gmail API via `google-api-python-client`
- **Database:** PostgreSQL (SQLAlchemy 2.0 + psycopg3)
- **Templating:** Jinja2 + Markdown + Bleach
- **Logging:** structlog (JSON output)
- **Hosting:** Railway (always-on service + Postgres add-on)

## Cost

For a single tenant at ~300 emails/month:
- Anthropic API: ~$3–4
- Railway: ~$5 (well inside the hobby plan's $5 included credit)
- **Total: ~$8–10/month**

Cost scales close-to-linearly with email volume. Prompt caching keeps the per-email cost low even with a large KB.

## Deploy (Railway)

1. Connect the GitHub repo to a new Railway project
2. Add the **Postgres** add-on; Railway auto-injects `DATABASE_URL`
3. In service variables, paste all keys from `.env.example` (Anthropic, Gmail OAuth, optional SMTP for alerts)
4. Set `DATABASE_URL=${{Postgres.DATABASE_URL}}` so the service references the add-on
5. Set a spending cap (~$10/mo) as a safety net
6. Push to `main` — Railway auto-builds and deploys

### Daily feedback sweep

Add a second service in the same project pointing at the same repo, but override:
- Start command: `uv run python main.py --daily-sweep`
- Restart policy: `NEVER`
- Cron schedule: `0 6 * * *`

### Verifying

Watch the logs:
- `pipeline_started tenant=<name> poll_seconds=60` — service is alive
- `tick_started count=N` — N threads to process this tick
- `classification thread_id=... category=... sensitivity=... confidence=...` — per-email decisions
- `draft_created thread_id=... draft_id=... category=...` — a draft is now in Gmail Drafts
- `kb_load_failed` or `pipeline_error` repeatedly → check the alert email or logs

## Roadmap

- **Daily digest email** — once-a-day summary to the owner: how many drafts, how many sent unedited, what categories spiked
- **Selective auto-send for proven-safe categories** — after weeks of feedback-loop data, narrow categories like "schedule lookup" can graduate from draft-only to auto-send. Sensitive categories (refunds, complaints) stay draft-only forever, hardcoded.
- **Service-account auth path for Workspace tenants** — eliminates the 7-day OAuth refresh token expiration when running production for Workspace customers
- **Web admin for KB editing** — for non-technical owners to update their own knowledge base without engineering involvement
- **Google Sheets sync** — for tabular content (pricing, schedule) that owners maintain in spreadsheets

## Why this is interesting

The technical surface is small — wiring Claude + Gmail + a database isn't novel. What's interesting is the **engineering discipline** layered on top to make drafts good enough to actually use:

- **Sensitive-category gating** that fails closed (no draft) when in doubt — most generic AI tools draft anything and hope for the best
- **Per-tenant brand voice** with few-shot examples — what makes drafts feel real instead of like ChatGPT default
- **Multi-tenant architecture from day one** — single-tenant deployment today, but adding tenant #2 is a config change, not a rewrite
- **Real-API tests, not mocks** — the surfaces most likely to break (Gmail, Claude) are tested against the real thing
- **Pipeline-level error isolation with the right invariants** — particularly: never apply the `processed` label until both the Gmail draft and the DB record are committed, so a partial failure doesn't cause double-drafting on the next tick

The feature is becoming table stakes — Microsoft Copilot will eventually ship something similar inside Outlook. The defensible angle isn't "we have AI"; it's "we drafted in your brand voice, grounded in your specific business, and we knew when not to draft at all."
